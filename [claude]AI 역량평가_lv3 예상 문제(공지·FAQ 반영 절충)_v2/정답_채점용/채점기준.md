공지·FAQ의 평가 방식: **문항별 요구사항 충족 여부 + 풀이 과정을 종합 평가**하고, **최종 코드 리뷰를 통과**하면 Level 3. FAQ는 문항 유형이 **"지시사항대로 구현하는 문제"와 "모델을 학습시켜 일정 성능 이상을 달성하는 문제"의 혼합**이라고 했습니다. 실제 세부 기준은 공개되지 않았으므로, 아래는 **이 모의를 스스로 평가하기 위한 가정**입니다.

## 2. 요구사항 표 (충족 / 미충족으로 표시)

| 소문항 | 충족 조건 | 흔한 미충족 |
|---|---|---|
| 1-1 | 개수·모양·dtype, id 불일치 **두 방향**, 원 레이블 고유값, 정리 후 분포, 불균형 비율 | 한 방향만 셈, 표기 흔들림을 못 봄 |
| 1-2 | std 기준 깨진 사진, 바이트 해시 중복 묶음 | 평균 밝기로 판단(어두운 정상 사진까지 제거) |
| 1-3 | BGR 판별 규칙, 밝기 지표, **train/test 밝기 분포 차이와 그 의미 서술** | 육안 검사 없이 규칙만, 분포 차이를 증강·검증과 연결하지 못함 |
| 1-4 | 다섯 규칙 모두, 엇갈린 중복은 묶음 전체 제거, BGR은 제거 아닌 복원 | BGR 사진 삭제 |
| 2-1 | 지정 순서, **모델 카드의 mean/std**, 검증 변환에 무작위성 없음 | ImageNet 값을 습관처럼 사용, 정규화 뒤에 밝기 변환 |
| 2-2 | `Dataset` 상속, `__len__`/`__getitem__`, long 정답, test는 -1 | 정답을 float로, 변환을 미리 한 번만 적용(증강이 매 epoch 같음) |
| 2-3 | 층화 분할, 표본별 역빈도 가중치, `replacement=True`, sampler와 shuffle 동시 사용 안 함 | 클래스별 가중치를 그대로 넘김, 비복원추출 |
| 2-4 | 밝기 증강 근거, 색조 금지 이유, **자르기 증강이 등급 레이블을 바꾸는 이유** | "성능이 좋아져서" 같은 근거 없는 서술 |
| 3-1 | `in_features`를 읽어 `fc`만 교체, 나머지 가중치 유지 | `Linear(96, 4)` 하드코딩(부분 충족) |
| 3-2 | 이름 접두어로 `requires_grad`, 리스트 반환, **범위 밖 BN을 `train()` 뒤에 `eval()`** | BN 고정 누락 |
| 3-3 | `log_softmax`+`gather`, 가중 CE는 가중치 합으로 나눔, focal γ=0이 CE와 같음 | `softmax` 후 `log`, 평균으로 나눔 |
| 3-4 | `train()`→BN 고정→**장치 이동**→`zero_grad`→순전파→`backward`→`step`, 표본 가중 평균, `eval()`+`no_grad`, CPU로 반환 | 입력만 GPU로 옮김, `eval()` 누락 |
| 3-5 | 최고 점수일 때만 `deepcopy(state_dict())`, 끝에 `load_state_dict` | 참조만 저장해 마지막 가중치가 됨 |
| 3-6 | 설정 2~3개를 **근거를 두고** 구성, 선택 기준을 val 계열로 정함 | test 점수로 선택, 한 번에 여러 요소를 바꿔 원인을 모름 |
| 3-7 | sample 순서, `index=False`, 형식 점검 통과 | 배열 순서로 저장 |
| 3-8 | 표의 수치를 인용한 비교, 선택 이유, 남는 위험·개선안 | 수치 나열만 |
| 4-1 | `Dropout`+`Linear(in_features, 1)` | 출력 5개 분류 헤드 |
| 4-2 | `digitize`, 좌표 탐색, 정렬 반환 | 임계값 순서가 뒤집힘 |
| 4-3 | 모든 조합, 시간 예산, 정렬된 결과·최고 params | 예산 무시, 결과 기록 없음 |
| 4-4 | baseline의 문제(학습 범위·과소적합)를 진단하고 그에 맞는 탐색 공간 구성, 기준 통과 | lr만 바꿈(fc만으로는 기준 미달) |
| 4-5 | `make_submission` 재사용, **정수** grade | 실수 저장 |
| 4-6 | 인접 등급 혼동 해석, baseline 대비 효과(수치), **개선안 2개** | 수치 나열만 |

## 3. 코드 리뷰 체크리스트

- [ ] 함수가 한 가지 일을 하고 이름이 그 일을 말한다
- [ ] 핵심 결정(왜 이 통계·증강·검증 기준·학습 범위인지)에 짧은 주석이 있다
- [ ] 크기·개수·클래스 수를 하드코딩하지 않는다(`in_features`, `len(...)`, `len(CLASSES)`)
- [ ] seed를 고정하고 커널 재시작 후 같은 결과가 나온다
- [ ] test 정답·test 점수를 학습·선택에 쓰지 않는다
- [ ] 원본 데이터를 바꾸지 않는다(`copy`, `clone`)
- [ ] 모델과 입력이 같은 장치에 있고, numpy로 바꾸기 전에 `.cpu()`
- [ ] 제출 파일이 `ps.check_submission`을 통과하고, 노트북 출력과 같은 실행에서 나왔다
- [ ] 서술 답안이 출력된 수치와 일치하고 다음 행동(개선안)으로 이어진다

## 4. 검증 결과 (2026-11-05, Windows 11, Python 3.12, torch CPU, torchvision 없음 → tv_compat)

- **정답 노트북**: 모든 셀을 위에서 아래로 실행해 오류 없이 끝났습니다(약 1.5~2분). 두 번 실행해 같은 수치가 나왔습니다. 로컬 채점 결과 Q3 0.918 / Q4 0.963 / Q5 0.996 → 세 문항 PASS.
- **버전 B(직접구현)**: 빈 상태로 끝까지 실행하면 처리되지 않은 오류 없이 끝나고, 소문항마다 `실패`를 출력하며 진행용 대체물로 이어 갑니다.
- **버전 A(빈칸)**: 빈칸 `___`은 정의되지 않은 이름이라, 채우기 전에 실행하면 그 셀에서 `NameError`가 납니다(정상). 모든 빈칸 줄이 정답 코드의 한 줄과 대응하는지 자동 대조했습니다.
- 이 PC의 작업 환경에서는 Jupyter 커널을 띄울 수 없어, 셀 코드를 순서대로 실행하는 스크립트로 검증하고 그 출력(글자·그림)을 정답 노트북에 저장했습니다. 문제 노트북 두 개는 출력이 없는 상태입니다. VSCode에서 직접 실행하면 같은 결과가 나와야 합니다.
- torchvision이 있는 환경(시험 환경으로 예상)에서는 실행해 보지 않았습니다. `tv_compat`은 torchvision.transforms.v2와 이름·인자를 맞췄지만, 난수 소비 방식이 달라 수치가 조금 다를 수 있습니다.
