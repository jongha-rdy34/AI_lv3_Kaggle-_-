# 채점 기준 (창작 가정)과 검증 결과

공지의 평가 방식은 "문항별 요구사항 충족 여부와 풀이 과정을 종합 평가하고, 최종 코드 리뷰를 통과하면 등급 부여"입니다. 실제 세부 기준은 미공개이므로, 아래 표는 **이 모의문제를 스스로 평가하기 위한 가정**입니다. 점수 대신 요구사항마다 충족/미충족으로 표시합니다.

## 1. 요구사항 표

| 소문항 | 충족 조건 | 흔한 미충족 |
|---|---|---|
| 1-1 | 개수·모양·dtype, 레이블↔이미지 불일치 두 방향, 원 레이블 고유값, 정리 후 분포, 불균형 비율 | 한쪽 방향 불일치만 셈, 표기 흔들림을 못 봄 |
| 1-2 | std 기준 깨진 사진, 바이트 해시 중복 묶음 | 평균 밝기로 판단(어두운 정상 사진까지 제거), 중복을 레이블 기준으로 찾음 |
| 1-3 | BGR 판별 규칙, 밝기 지표, **train/test 밝기 분포 차이 발견과 그 의미 서술** | 육안 검사 없이 규칙만, 분포 차이를 증강과 연결하지 못함 |
| 1-4 | 다섯 규칙 모두 적용, 레이블이 엇갈린 중복은 묶음 전체 제거, BGR은 제거 아닌 복원 | BGR 사진 삭제, 엇갈린 중복 중 하나를 남김 |
| 2-1 | (N,3,H,W) float [0,1], **모델 카드의 mean/std** 사용 | `reshape`로 축 변경(픽셀 섞임), train 통계로 바꿔 씀 |
| 2-2 | 샘플별 반전·밝기, [0,1] 자르기, 입력 불변, **색조 변환 금지 이유 서술** | 배치 전체에 같은 변환, `clamp` 누락, 원본 텐서 수정 |
| 2-3 | 층화 분할, 역빈도 가중 복원추출 | 비층화 분할, 비복원추출 |
| 3-1 | `in_features`를 읽어 `fc`만 교체, 나머지 가중치 유지 | `Linear(96, 4)` 하드코딩(부분 충족), 모델 전체 재초기화 |
| 3-2 | 이름 접두어로 `requires_grad`, **범위 밖 BN을 `train()` 뒤에 `eval()`** | BN 고정 누락 → running 통계 변화 |
| 3-3 | `log_softmax`+`gather`로 구현, 가중 CE는 가중치 합으로 나눔, focal γ=0이 CE와 같음 | `softmax` 후 `log`(수치 불안정), 평균으로 나눔 |
| 3-4 | `train()`→BN 고정→증강→정규화→`zero_grad`→`backward`→`step`, 가중 평균 손실, `eval()`+`no_grad` 추론 | 정규화 후 증강(밝기 범위 깨짐), 마지막 배치 누락 |
| 3-5 | 전략·검증 기준을 **근거와 함께** 선택, 두 검증 결과 비교, 위험 서술 | test 점수로 선택, 근거 없는 선택 |
| 4-1 | `Dropout`+`Linear(in_features, 1)` | 출력 5개 분류 헤드(요구와 다름) |
| 4-2 | O·W·E 행렬로 QWK, sklearn과 일치 | 가중치 (i-j)²만 쓰고 정규화 누락(값은 같지만 정의 이해 확인), E를 n으로 안 나눔 |
| 4-3 | `digitize`, 좌표 탐색, 정렬 반환 | 임계값 순서가 뒤집힘 |
| 4-4 | 모든 조합, 시간 예산, 정렬된 결과·최고 params | 예산 무시, 결과 기록 없음 |
| 4-5 | 인접 등급 혼동 해석, 탐색 결론, **개선안 2개** | 수치 나열만 |
| 5-1 | 역할·JSON만 출력·8개 필드 자료형·정규화 규칙·**미확정→null**·예시·구분 기호 | "JSON으로 줘" 한 줄, 추측 금지 규칙 없음 |
| 5-2 | required·additionalProperties·null 허용·enum·배열 원소 스키마 | `type: "integer"`만(null 불허), 원소 스키마 없음 |
| 5-3 | 중괄호 구간 추출, `json.loads`, 끝 쉼표 수리, `literal_eval`, 실패 시 None | 예외를 그대로 올림 |
| 5-4 | 모든 정규화 규칙, 화씨 판단, g→mg, 사전 밖 → null, **bool을 정수로 받지 않음** | `int(True)=1` 통과, 모르는 값을 추측 |
| 5-5 | 키 집합, 정수/숫자 필드에서 bool 제외, enum, 배열 원소 검사 | `isinstance(v, int)`만 써서 True 통과 |

## 3. 검증 결과 (2026-11-04, Windows 10, Python 3.12.2, torch 2.5.1+cpu)

- 정답 노트북: nbconvert로 끝까지 실행했습니다. 오류나 진행용 대체 입력 사용 없이 끝났고 약 4~5분 걸렸습니다. 두 번 실행해 같은 수치가 나오는 것도 확인했습니다.
- 빈칸 문제 노트북: 처리되지 않은 오류 없이 끝까지 실행됩니다(약 50초). 소문항마다 `실패`를 출력하고, 데이터 준비 단계는 진행용 입력으로 이어 갑니다.

| 문항 | 정답 노트북 결과 (validation) | test (로컬 채점) | 함께 확인한 비교 |
|---|---|---|---|
| Q1 | 1,632장 → 정제 1,587장. 깨진 12, 중복 묶음 22(엇갈림 7), BGR 30. 어두운 사진 train 8.1% / test 38.0% | — | — |
| Q2 | 균형 재구성 비율 0.25±0.01 | — | — |
| Q3 | CE: val 0.960, **val_dark 0.935** / sampler: val 0.938, val_dark 0.912 → CE 선택 | macro-F1 **0.881**, multiple 재현율 0.48 | 6 epoch CE는 val 0.919인데 test 0.798(val_dark 0.763이 test에 가까움). sampler 10 epoch의 test는 0.906 |
| Q4 | lr 3e-3 0.965, 1e-3 0.949, fc만 0.832. 고정 임계값 0.934 → 최적화 0.965 | QWK **0.943** | — |
| Q5 | dev 필드 정확도 0.959 (정규화 없이 0.703), 파싱 실패 1, 자료형 위반 0 | 필드 정확도 **0.996**, 키 불일치 0 | 복구할 수 없는 경우: 끊긴 응답, 빠진 키, 근거 없는 추측값 |

해석
- **Q3의 교훈:** 일반 validation은 test의 밝기 분포를 반영하지 못해 점수를 낙관적으로 보여 줍니다. 1-3에서 찾은 분포 차이를 반영한 `val_dark`가 test와 더 비슷하게 움직였습니다. 다만 소수 클래스가 validation에 17장뿐이라 어떤 전략이 나은지는 흔들립니다. 정답의 선택(CE)이 test에서 가장 좋은 선택은 아니었고(sampler 0.906), 이는 시험에서도 생길 수 있는 일입니다.
- Q4 임계값은 같은 validation으로 맞췄으므로 validation 점수가 약간 낙관적입니다(val 0.965, test 0.943).
- Q5는 정규화 규칙을 잘 쓰면 모의 응답의 형식 오류 대부분을 복구할 수 있습니다. 실제 LLM에서는 프롬프트 품질이 응답 자체를 바꾸므로 5-1의 중요성이 더 큽니다. 이 세트에서는 그 효과를 측정할 수 없습니다.
